# 会計・データ設計

## 会計の分け方

| 対象                   | 販売額・収入                      | 利益計上する原価                                                 | 個人請求                     |
| ---------------------- | --------------------------------- | ---------------------------------------------------------------- | ---------------------------- |
| 通常注文               | 欠品修正後の数量×その回の販売価格 | 納品書総額から同じ納品書の行事注文全体・直接の園内販売仕入を引く | 購入者ごとに加算             |
| 園内販売               | 売れた数量×販売価格               | 売れた数量×仕入単価                                              | 購入者を指定したときのみ加算 |
| 即時入金の園内販売     | 同上                              | 同上                                                             | 加算しない                   |
| 行事使用分             | 仕入単価×使用数を財政へ請求       | 通常販売利益へ含めない                                           | 加算しない                   |
| 行事の未処理余剰       | まだ請求しない                    | まだ販売利益へ含めない                                           | 加算しない                   |
| 行事から園内販売へ振替 | 売れたときに販売額                | 行事の実際の仕入単価を引き継ぐ                                   | 販売先に応じる               |
| 過去実績               | 判明していれば保持、不明はnull    | 判明していれば保持、不明はnull                                   | 対象外                       |
| 利益調整               | 架空の販売額を作らない            | 架空の仕入額を作らない                                           | 対象外                       |

例：同じ納品書に通常注文400円と行事20個×138円があるとき、税込総額3,160円を入力し行事を関連付ける。通常注文原価は400円。18個使用の財政請求は2,484円。余剰2個を振り替えた販売側仕入は276円。200円で2個売れた場合の園内販売利益は124円。売れ残りがある場合は売れた分だけ原価・利益を計上する。

行事の注文数全体を通常注文の納品書から分けるため、未処理余剰も誤って通常注文の原価には入らない。商品を手動で個人へ割り振る以外に欠品を自動配分する処理はない。

## 日付と年度

- 4月1日〜翌3月31日。通常注文は納品日、園内販売は販売日、過去実績は登録した実績日で計上。
- 利益調整は指定年度。日付なしの場合は年度全体に含め、任意期間からは除き「日付未設定」と表示する。
- 注文回単位の個人請求は、その回の通常注文＋その回へ集金をまとめた園内販売。期間集計の個人請求は納品日・販売日で集計する。両方を足して請求しない。
- 仕入額未確認の回の利益は未確定。分かっている利益の合計を暫定値として表示し、未確定件数を明記。
- 利益のみの過去実績を含む場合、販売・仕入は「判明分」と表示し、総額と誤認させない。

## 保存構造

少人数・小さいデータを対象に、Supabase Postgresの1ワークスペースに構造化JSONBを保存する。中身はIDで結ばれた独立コレクションで、後から商品別・購入者別にJSONB展開して集計可能。

- `products`: 商品マスター、税込価格、価格方式、個別価格、仕入単価、カテゴリー、期間
- `buyers`: 購入者と固定注文
- `rounds`: 納品日、価格スナップショット、個人別数量、注文確定時数量、状態、納品書総額と仕入区分のリンク
- `events`: 行事の商品別注文数・使用数と仕入単価スナップショット
- `stocks`: 園内販売ロット、元の行事商品へのリンク、数量、販売・仕入単価
- `sales`: 販売日、数量、販売先、即時入金、集金先注文回、価格スナップショット、取消フラグ
- `history` / `adjustments` / `goals`: 過去実績、年度利益調整、年度目標

`wappan_save` RPCで全体をトランザクション保存。現在revisionとの一致を必須にし、同時編集で古いデータが新しい保存を上書きしない。競合・通信失敗時には保存済みと表示しない。入力は画面に残す。競合時は変更を控えて最新読込後に再入力する。オフライン自動保存・自動マージは行わない。

全保存を`wappan_revisions`へ記録し、変更前も含めた履歴を永続保持する。通常の注文・販売は自動削除しない。販売取消は履歴を残して残数・請求・利益を戻す。過去実績と調整の削除・テスト注文削除も更新履歴から追跡可能。

## 安全性

- 主保存先はクラウドDB。localStorageはSupabase SDKによるログインセッション保持のみ。業務データ・注文下書きの保存先にはしない。
- 係のUUIDを`wappan_staff`へ登録。認証済みでも未登録者にはアクセス不可。
- anonのテーブルアクセスなし。authenticatedはRLS付き参照のみ。書き込みは係確認・revision検証・整合性検証をするRPCのみ。
- Secret / Service Roleキーをフロントエンドへ置かない。外部へExcel内容・個人名を送って解析しない。
- Reactのテキスト表示を使用し、入力文字列をHTMLとして注入しない。
- 商品マスター変更は過去の注文回へ波及しない。この回の価格を明示的に編集した場合のみ、確認後にその回の集金を再計算。
- DBの更新ログには個人情報が含まれるため、同じRLSで保護する。

## Excel読み取りの限界

商品名と「税込」の見出しから列を推定し、左右に並んだ商品ブロックも扱う。自動で特定できない表はシート・列・開始行を選択する。読めた候補を表示し、登録前に必ず修正・確認できる。重複行は初期選択から外し、正規化した同名商品を更新する。手動の既存商品への対応付けも可能。

実物の毎月の注文表が今回のリポジトリにはないため、その固有レイアウトでの抽出網羅性は未確認。検証用xlsxでは商品名・税込価格・複数ブロックを確認する。数式セルに計算結果が保存されていない場合などは価格を抽出できず、候補から漏れる可能性がある。元表との照合を必須とする。
