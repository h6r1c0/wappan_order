この文書は**変わり得る業務仕様**を扱う。開発思想は [AGENTS.md](../AGENTS.md)、視覚と操作は [UX基準](ux-finish-checklist.md#今後の変更に適用するux基準)、検証手順は [DEVELOPMENT_CHECKS.md](DEVELOPMENT_CHECKS.md)。価格・日付・人物の例は現在の本番値や恒久的な定数を意味しない。仕様変更時は対象コードとテスト、確認できる利用者の判断を照合してここを更新する。

## 記録の帰属と計算

| 区分 | 根拠・記録 | 個人請求と年度計上 |
| --- | --- | --- |
| 個人注文 | 注文回の商品価格、実渡し数、カット代、欠品・取消 | 対象回の購入者へ請求。年度の通常売上・原価は対象回の状態に従う |
| 販売用 | 在庫ロット、販売数量・価格・原価、販売先、集金先回 | 後日個人請求、外部販売、即時入金を分け、販売先訂正で売上を重ねない。売れた分の原価だけ計上 |
| 行事 | 実使用数×対象商品の仕入単価 | 財政請求、通常の販売利益から除外。余剰を販売側へ振り替える際は原価も移す |
| おやつ | 財政・家庭直接・共通単価の用途別数量から実使用数を導出し、販売振替と入荷残を照合 | 家庭の共通単価請求と職員の実原価による財政請求を分離。振替・在庫・利益の二重計上を防ぐ |
| その他販売 | 商品名・販売日・数量・単価・原価・受取状況 | パンの発注・在庫・個人集金と独立。原価0円は有効な数値で、原価未確定とは別。年度へ一度だけ計上 |
| 過去実績・利益調整 | 実績日または対象年度と根拠 | 架空の注文・仕入・現金受取を作らず、詳細実績との二重算入を防ぐ |

計算と保存の詳しい構造は [DESIGN.md](DESIGN.md)、`src/domain.js`、`src/commerce.js`、`src/snack-billing.js`、`src/other-sales.js`、関連する `tests/` を照合する。`null` の原価・価格を0円とみなして完了させない。家庭向け共通単価150円は過去の運用例で、将来の固定価格ではない。対象商品の数量×今回の確定済み仕入単価から加重平均し、10円単位に切り上げた候補を提示する。手動指定・確定済みの単価を勝手に上書きしない。

おやつは財政・商品を指定した家庭への直接割当・商品別数量を明示した共通単価・余剰の販売振替を独立に記録する。区分の途中保存は請求・集金を増やさず、本人が保存済みの区分を照合して確定した請求だけ個人集金に反映する。おやつ名は任意。共通単価は財政数量から自動生成しない。販売用からおやつへ移した商品は元のロット・原価・納品回を参照し、元在庫の残数を減らすが、二度仕入れない。仕入原価が未確定なら推測せず、請求・利益の確定前に確認する。その他販売の購入者割当は既存の販売実績へ帰属先を付け、売上・原価をもう一度作らず個人の未収へつなぐ。旧受取原本は変更しない。

販売用から共通単価のおやつへ振り替える際は、既存グループを選んで数量を追加でき、グループの食数・名称・手動単価を保つ。新しいグループは明示的な選択だけで作成する。保存済みの別グループの統合・訂正は本人の操作と理由を履歴に残す。商品数量・用途・請求の差が未確認なら既存値を保ち、後から元記録を理由付きで訂正する。現金受領原本を請求訂正で消さず、請求との差を別に把握する。通常の仕分けに追加の確認・入力を課さない。

財政から実際に受け取った現金を記録する場合は、おやつの記録に受領日・受領額を請求とは別の事実として保存する。請求訂正は受領原本を変更せず、受領記録の誤りは理由付き訂正で元記録を履歴に残す。受取額を売上や利益へ再加算しない。請求との差の説明メモは必要時だけ保存し、返金・精算済みを自動判定しない。

**2026-11-05最新の確定条件**：発注・実入荷・販売用振替・財政分・家庭直接分・家庭共通分を区別し、実使用数は財政＋直接＋共通の商品別数量から導出する。独立した実使用数入力・転記は廃止する。発注数＝実使用数と推測せず、実入荷との差を用途未振分として残す。旧画面の `line.used` は当時の保存・訂正履歴として保持し、用途別記録と矛盾しても原本を消したり再入力させたりしない。販売振替は請求確定前にでき、二重振替を防ぐ。財政請求は確定した財政区分の数量×当該ロットの確定済み仕入単価だけで計算し、未確定なら金額を未確定とする。保存済み財政区分は請求確定前でも区分単独で編集・保存可能だが、正式な財政請求や家庭集金にはしない。おやつ使用原価は請求額と別に表示する。既存の振替・家庭割当・受取を保存し直さない。振替元原価の未登録・訂正は対象回のロットと連動記録だけに反映し、確定済みの他回価格を変更しない。直前の『使用数を独立保存する』記述は今回の実機訂正で撤回された。

納品書税込合計が当該注文回の仕入を網羅し、同日の販売用在庫がすべて販売済みで行事等の原価が確定している場合、個人注文と販売用を合わせた利益は「両方の売上−納品書総額」で算出できる。販売用の個々の原価が不明でも全体利益だけは確定可能とし、個人注文と販売用の個別利益へ推計配分しない。未販売在庫や別日の売上・振替・セット販売がある場合は、該当する原価を確認する。販売用の購入者請求と個人請求外の支払済み販売を両方売上へ含め、同じ販売を再計上しない。受取・未収は利益に加算しない。`roundAccounting` と `tests/domain.test.js` を参照する。

## 注文回と価格改定

注文回の進行表示は `roundProgress` で、保存された旧値（入力中・注文確定・納品済み・精算済み）と納品・利益・請求・受取・未解決事項から導出する。利用者向けには入力中→注文確定→納品済み→集金中→完了の5段階を示す。内部の精算完了判定は `roundSettlementStatus` に残し、現金集金と混ぜない。今回分の元請求が全額回収され、必要な精算と確認が済めば自動完了する。別の注文回の過去未収は完了を妨げない。

今回分に未収が残ったまま集金業務を終える判断だけは係が行い、`rounds[].collectionClose` に終了日時とその時点の元債権別残高を保存する。元の請求・現金・充当を複製・減額しない。完了後も元の債権へ後日充当でき、残高がゼロなら「未収繰越あり」の表示だけが消える。終了後に新たな未収が増えたり、請求・販売・納品の重大な不整合が生じたりした場合は再確認へ戻す。請求訂正によって未収が増えた後に再終了する場合は以前の終了判断を `history` に保持する。保存は従来のrevision競合検出とDB検証を通す。`tests/round-progress.test.js` と `tests/round-close-database.test.js` を参照する。

LINE等の貼り付けは、個人注文・販売用・おやつ用を区分した確認画面で商品と数量を照合してから一括保存する。区分・購入者・商品が曖昧な行を推測で確定しない。既存の数量は上書きせず、取込済みの同じ内容の再保存を防ぐ。`tests/batch-import.test.js` を参照する。

未照合の行は `rounds[].pendingImports` に元文・商品名・数量・用途・購入者とともに保留し、正式な注文・発注・請求へ加えない。確認済み行は先に保存し、保留行は商品追加後にその行だけ登録する。販売単位が違う商品は別IDとし、1個入りを3個入りへ照合しない。商品表にない今回限りの商品は対象回の手動価格と出典を記録できる。2026年10月16日の白パン1個入り120円は利用者から確認された当回の販売実績としてだけ入力候補に出し、将来の正式価格へ転用しない。`src/batch-import.js` と `tests/import-hold-diff.test.js` を参照する。

Excel取込の前回比較は `productImportHistory` の保存済み商品表を正とする。過去の取込履歴がない場合の現行マスターとの比較は、その旨を明示する。税込価格の差、販売単位、掲載開始・終了を区別し、比較表示だけで既存回の取引金額を変更しない。

注文回を画面から作る際は、作成時点の固定注文を同じ保存操作でその回の注文として保持する。後日の固定注文設定変更は既存回の数量を変更しない。価格未決定の数量も保存し、商品表の価格は未請求の対象回に反映する。請求・受取済みの回を商品表再取込だけで改算しない。価格候補は既知の商品との比較検証に十分な精度があるときだけ提示し、採用は対象回ごとに明示する。

`rounds[].products` に対象回の商品・販売価格・原価などのスナップショットを保持し、各注文と集金はその回を参照する。商品マスターを更新しても過去回を遡及変更しない。注文回の価格を明示的に訂正する場合は差分・履歴・請求への影響を確認する。Excel取込や再編集でも使用済み回の価格を無断で上書きしない。月をまたぐ旧回の精算と新回の発注を並行できる。未公表の将来価格を本番へ仮登録しない。検証は `tests/domain.test.js`、`tests/excel-lifecycle.test.js`、`tests/commerce-line.test.js` など。

## テスト区分と年度実績

`round.test=true` の通常注文は `report` の年度通常売上・利益から除外され、販売用は紐づく `stock.test`、行事は `event.test`、おやつ請求は `event.test`、その他販売は記録自身の `test` で除外する。2026年9月11日は確認時点でテスト区分を維持する例であり、永続的な切替禁止ではない。

集計画面の「テストを含める」は読み取り専用の検証表示。正式実績の `test` と `collectionLive` を変更せず、年度全体、期間指定、納品日別内訳、目標進捗へ同じ条件を適用する。仕入が未確定の行は確定利益へ見せかけない。納品・仕入・売上から計算できる精算状態は `roundSettlementStatus` で導出し、現金集金とは独立する。旧DBの「精算済み」保存検証には未使用行の原価まで要求する条件があるため、手動の状態変更は使わず、計算可能性と納品確認を表示条件とする。

注文回の「注文の詳細」から利用者の確認を経て `setTest` で切替可能。関連する行事・販売用在庫にも区分を伝播し、集金先に紐づく販売記録との区分不一致は拒否する。切替の前には同日過去実績との二重計上、売上・原価・利益・財政請求、請求・受取・充当・訂正への影響を確認する。`collectionLive` はテスト回の集金債権を通常回の繰越へ含めるための別条件であり、年度実績を本番へ算入するスイッチではない。利用者の判断なしに本番の区分を変更しない。`docs/ACCEPTANCE.md` の9月11日例は初期の操作資料として読む。

## 請求・案内・受取・充当・訂正

- `collections` は通常注文・後日請求の販売・家庭向けおやつ請求を対象回で合算する。`billingReviews` の案内額と、`receivableItems` の既知の追加請求は現金受取を証明しない。商品・数量・単価の未確定は請求前照合と印刷前に示し、解決済み警告は未処理として繰り返さない。
- `collectionEntries` は受取原本。請求確認だけで作らない。通常の予定額全額受取は一操作、例外は受取額・理由・過去未収・預かり・未解決差額を区別する。受取・預かりの回収は新たな売上や利益ではない。
- `collectionAllocations` は**既存受取の充当先に関する別の判断**。受取金額だけで古い請求から順に割り当てない。複数債権に対する曖昧な一部受取は `unallocated` とし、請求別の支払済み表示を確定しない。複数先への金額分割は受取額と一致させる。一受取に有効な充当指定は一件。
- `collectionCorrections` は受取原本・支払済み確認の取消根拠。元記録と既存充当履歴は監査のため残すが、訂正済み受取・確認は `effectiveCollectionState` で現在の債権計算から除く。訂正済み受取に新しい充当指定を追加しない。`20261023073903` と `20261023075806` のDB migrationは参照・金額・一意性と訂正後の監査履歴を検証する。過去の受取内容を新コードの推測で書き換えない。
- 元の受取日が不明な過去預かりは `collectionCredits.date=null` と登録日時を区別し、`appliedTo` で本人が指定した請求にのみ充当する。既に充当した100円を返金へ再利用できない。現金の今回受取とは別であり、預かりの充当だけでは今回の残額を入金済みにしない。旧形式の預かり記録は従来どおり読める。
- 保存は `wappan_save` のrevision照合と履歴で競合・直接更新を防ぐ。本番作業中は開始時のrevisionを上書き対象として固定せず、保存直前に最新を再確認する。復旧用コピーに個人情報が含まれるため公開リポジトリに置かない。
- 注文回の「最近の操作」は既存の `wappan_revisions` の成功済み差分から読み取る。ログインアカウントは履歴の `updated_by` と対応するメールアドレスで示し、メールアドレスを個人名と推測しない。自由記述の注文回メモと操作履歴は別に扱う。

## 販売先・欠品・印刷

販売用の注文、納品、欠品・振替、割当、販売待ち、販売先不明を分ける。1個ずつ異なる先へ分割でき、購入者から複数商品もまとめられる。途中入力と訂正履歴を保護する。欠品は注文原本を保ち、確認した実渡し数を請求へ反映する。印刷できない条件は押す前に示し、案内済み帳票と訂正後帳票を混同しない。`src/shortages.js`、`src/collection-workflow.js`、`src/print-*.js`、対応テストを確認する。


## 2026-11-07 継続開発での補足

おやつから販売用への振替は、財政・直接・共通単価の確定を待たず、利用者が数量を指定して独立保存する。全残数の自動振替はしない。元の振替在庫IDの数量を理由付きで直接訂正し、減らした差分は元のおやつ商品の使用可能数量へ戻す。販売・セット使用・再振替済み合計未満への減数は拒否する。数量訂正で商品原価、既存販売、確定請求、家庭数、手動単価、現金受取を変えない。実績未確認の本番数量は開発側で訂正しない。

表示上の同商品集約は在庫履歴や請求を再作成しない。逆方向の誤振替を本人が明示取消する場合も、既存共通単価グループのID・名称・手動単価は残す。対象が空になったグループは明示数量0個・家庭割当なしとして保持できる。元行は監査履歴に残す。

集金では、過去回だけに属する未充当受取があっても、今回の未収項目が特定でき、その額を現在総残高が下回らない場合、今回分の明示受取を妨げない。過去受取を推測充当せず、今回の新しい現金だけを当該項目へ記録する。今回回の未充当受取や額の不整合があれば、先に履歴を確認する。誤受取取消と二重受取防止は継続する。

### 2026-11-07 PR #36後の実務訂正

元の販売振替数量の訂正は、別の仕分け区分が編集中でも独立保存できる。編集中の区分は保持し、数量訂正に便乗して確定・保存・破棄しない。販売済み・再振替済み数量による下限を数で示し、訂正結果と履歴を同じ商品へ即時表示する。保存前検査の失敗も訂正位置に表示する。新規振替の未割当残数0の制約は変えない。

### 2026-11-07 PR #37後の集金と画面

旧形式の受取に請求IDがなくても、受取が属する注文回の時点で唯一の請求がある場合は、その請求へ読み取り計算上で充当する。後日の新しい請求を旧受取の候補へ混ぜない。受取時点に複数の未収があり一意に決められない場合は原本の充当先を推測せず、終了判定を止めて内訳確認を求める。元の受取日・額・訂正・明示充当の履歴を変更せず、現金を再登録しない。今回の未収繰越は元の注文回に属する確かな残額だけを人数・金額として表示する。`tests/collection-legacy-round.test.js` を参照する。

販売用の残数・販売先、おやつの区分保存、請求監査、集金残を注文回の保存済み事実から短く表示する。販売の実績未回収なら商品利益は現時点の額として示し、確定済みの個人請求の受取は進められる。おやつの5工程は開閉でき、切替え時も編集中の値を保つ。財政・個別・共通単価の保存は途中保存で、請求確定時だけおやつの家庭分を集金へ反映する。確定後の訂正は理由と履歴を保持する。
# 仕入先への支払いと外部売上金の引渡し（2026-11-13本人確認）

- 購入者からの受取、売り子から係への外部販売代金の引渡し、仕入先への振込は別の現金履歴。売上・利益・個人未収を振込や引渡しで再加算・減算しない。
