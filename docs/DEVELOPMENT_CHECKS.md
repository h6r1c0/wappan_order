# 開発開始・検証・報告の手順

最上位方針は [AGENTS.md](../AGENTS.md)、業務の正本は [BUSINESS_RULES.md](BUSINESS_RULES.md)、画面の正本は [UX基準](ux-finish-checklist.md#今後の変更に適用するux基準)。本書は**手順・検証の正本**。個別の過去の結果は [初期記録](VERIFICATION.md) と [過去の受入例](ACCEPTANCE.md) に残し、現在の件数や本番状態へ転用しない。

## 開始前

1. `git status`, 最新mainと対象ブランチ・未マージ差分、直近コミット、関連する文書・実装・テスト・migration・CIを確認。別作業が進んでいれば上書きしない。
2. 利用者の目的、確定した変更、維持する仕様、未確定の意思決定、同種の問題が及ぶ調査範囲、実際に触る範囲を分ける。保存・会計と前後工程への影響を洗い出す。
3. 本番を扱う場合は最新revision・主要件数・ハッシュを読み取り、必要な復旧用コピーを安全に確保する。利用者の作業中の追加保存を想定し、テスト操作は隔離環境にする。個人情報や鍵をGitへ入れない。

## 実装と検証

開発途中は変更箇所と影響範囲に応じたテストを選ぶ。金銭・数量・保存・認証・互換性の境界条件は省かず、発見した重要な不具合は回帰テストに残す。成功済みの検証は関連部分が変わらなければ再利用し、環境起因の失敗とアプリの失敗を分ける。全体検証は影響とリスクに応じて行い、GitHub Actionsの結果も利用して同じ作業を不要に繰り返さない。必要な検証の未完了と残るリスクは最終報告に明記する。

| 対象 | 必要な確認と入口 |
| --- | --- |
| 会計・価格 | 対象回価格、数量、欠品、売上・原価・利益、未収・預かり・充当、テスト除外の前後値。`npm test`、`tests/domain.test.js`、`tests/collection-*.test.js`、`tests/snack-*.test.js`、`tests/other-sales.test.js` |
| DB・保存 | `supabase/migrations/` の順序と既存JSON互換、PGliteでRLS/RPC/revision/訂正・監査を検証。競合、失敗、再読込を含む。migration適用後は本番revisionと保存ハッシュを再照合 |
| 業務画面 | `tests/browser/` のChromium・WebKit、320/375/430pxとPC。未入力・一部・完了、欠品、販売先分割、通常/例外集金、再開、訂正、印刷前制御 |
| UX | 同じデータ・幅で操作数、遷移数、行高、スクロール、重複情報、入力の保持、状態の読みやすさ、保存後の次工程を比較。実画面・スクリーンショットも確認 |
| 配布 | `npm run build`、GitHub Actionsのverify/deploy、main SHAと公開ファイル、配布後の本番業務データの差分を確認 |

列挙外でも価格未設定・原価0と未確定・0件・長い名称・高額・一部受取と複数請求・連続操作・訂正後再開・競合・月跨ぎなどを組み合わせる。組合せが膨大なら金銭・データ消失・業務停止に関わる境界値と状態遷移を先に検証する。検証できなかった実機・認証後本番操作は明示し、利用者に再現を求める前にAI側で検証する。

## 変更の根拠と完了判定

- 個別の指摘を同種の部品・他工程まで調査し、確認した問題だけ修正。通常の手順が以前より増えたら未完成。修正後に同じシナリオと隣接する回帰を再実行。
- 新しい**確定仕様**は業務正本、共通UXはUX正本、再発条件は必要なテストに追加。仮説や個別の検証金額は恒久ルールにしない。
- PR/報告は「参照した原則と現状」「変更と維持」「調査範囲と変更範囲」「検証と前後比較」「見つけた問題」「本番への影響」「未検証」「コミットと公開」を短く示す。テスト件数は実行時の結果を使う。
- 文書のみの変更ではアプリ本体・migration・業務データに差分がないか確認し、リンク・正本・古い記録との関係を検査する。`npm run check:docs` を用いる。

## 文書だけで行う模擬レビュー

依頼「集金一覧のボタンが目立ちすぎる。もっと使いやすくして」の場合：

1. 集金の通常業務と本人が先に見る名前・予定額・受取状態を確認し、ボタンの視覚的な強さ、共通部品・工程色・タップ領域を調べる。
2. 同じ役割のボタンが注文・納品・販売等にもあるか調査する。問題が確認できた箇所と必要な共通部品だけを変更候補にする。
3. 全額受取1操作、例外時だけ詳細、受取事実と案内/確認の分離、監査履歴・revision保存を維持する。
4. 同条件の変更前後画面で密度・押し間違い・視認性・操作数を比較し、通常/例外・訂正・競合を検証する。会計と本番データの差分を確認して報告する。

これは作業方針の検査例であり、実画面の変更や本番受取の操作を指示しない。
