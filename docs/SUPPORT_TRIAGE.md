2. [業務・保存仕様](BUSINESS_RULES.md)、[開発・検証手順](DEVELOPMENT_CHECKS.md)、[要望台帳](REQUEST_LEDGER.md)の関連IDと最新の本人実機結果を照合する。画面操作は該当する `src/` と `tests/browser/` を確認する。古い結果は現在の成功の証明にならない。

## 利用者に案内する業務の境界

注文→発注→納品・欠品→個人／販売用／おやつの仕分け→請求確定→購入者の集金→仕入先への振込記録。個人仕分け表は個人注文の品物がある人、集金袋ラベルは当該回の個人請求がある人を対象とする。

販売・請求・現金受取・充当・返金・預かり・仕入先振込は別の事実。外部販売の売上と売り子から係への現金引渡しも別に記録する。後日回から元の請求を指定して受け取った金額は元請求へ反映する。取消済み現金は除外し、充当先のない預かりを未収へ自動充当しない。10月16日以前の仕入先支払完了は本人確認情報であり、個別の振込日・額は未記録。

操作の詳細が公開版と一致しないときは一般論で案内せず、画面名・対象回・現行版を確認する。公開マニュアルは別途制作中のため、古い作業初稿を利用者向け正本と呼ばない。

### よくある判断の入口

- 「後の回で受け取ったのに元の回が未収」：受取の対象請求ID、取消、充当先未確認の預かりを区別し、金額と二つの画面を照合する。現金を再登録しない。
- 「おやつ請求を訂正したい」：個別・共通・財政のどの割当かを確認し、途中保存と確定請求の再確定を区別する。受取前の請求訂正を返金扱いしない。PR #46の新しい動線は公開確認後に案内する。
- 「財政へ多く請求した」：請求済み数量、受領済み現金、最終精算予定・実施を別に確認する。元の請求を勝手に書き換えない。
- 「外部販売の現金を受け取った」：商品売上は既に計上済みであり、売り子から係への引渡しだけを記録する。本人の受取事実と本番保存結果を確認する。

## 受付と対応

将来のフォームは一本とし、報告種別（質問／不具合／改善要望）、報告者、画面、困りごとを基本とする。実際に起きたこと・期待したこと・連絡方法は必要に応じて任意。スクリーンショットは必須にしない。Googleフォームのファイルアップロードは回答者のGoogleログインを要するため、初期版で必須項目にしない。

回答原文はフォームの回答タブに保ち、担当者の調査・回答は別の「対応管理」タブへ受付番号と共に記録する。状態は「新規／調査中／回答待ち／開発中／実機確認待ち／解決」。管理列は受付番号・日時・種別・報告者・画面・内容・優先度・担当・状態・調査／回答・Issue/PR・解決日・追加確認を基本とし、原文は編集しない。重大な請求・現金・データ消失・二重集金は最優先。回答者へ必要な返信方法、通知先、担当者権限はフォーム公開前に確認する。原文や個人情報を公開GitHub Issueへ転載しない。

一次担当は現行仕様と報告内容を照合し、質問なら根拠付きで回答、不具合なら再現条件・影響と関連要望IDを整理する。開発が必要ならWorkへ「現象／再現条件／保存事実／期待結果／変更禁止事項／本人判断待ち」を引き継ぐ。Workは隔離データで実装・テスト・PR・公開を担当する。しょうこは現場の受取事実、本番訂正、承認、必要なiPhone実機確認だけ判断する。

## フォーム一本で始める具体案（当時の設計。2026-11-21、下書き作成済み）

用途別に分けると入口・通知・台帳の管理が増える。一本にまとめ、報告種別で分ける。

| 項目 | 入力 | 必須 |
| --- | --- | --- |
| 何について | 質問／不具合／改善要望／分からない | 任意。未入力は一次受付側で分類 |
| お名前 | 短文 | 任意 |
| どこで困りましたか | 注文／発注／納品・精算／集金／集計／印刷／ログイン／その他・不明 | 任意 |
| 困っていること | 長文一つ。起きたこと・希望は分かる範囲で一緒に書ける | 必須 |
| 対象の注文回 | 日付または短文 | 任意 |
| 返信先 | 本人が返信を希望する場合だけ入力。認証済みメールの自動収集は初期案にしない | 任意 |
| 画像 | 初期フォームにはアップロード質問を置かない。必要時だけ既存の連絡方法で追加確認 | なし |

ファイル添付は**任意の質問でもログインが必要**になるため、単に必須を外すだけでは操作負担を減らせない。画像なしの送信を基本にする。「回答を1回に制限」もログインを要求するため初期案では無効。回答者用の公開範囲と、フォーム編集者・回答Sheetの管理権限を別々に検証する。

### 台帳と履歴の構造

- 原文タブ：Google Formsの回答列だけ。担当者が原文を修正しない。自動取得する受付日時と原文行の対応を維持する。
- 対応管理タブ：受付番号（例 `WAP-S-000001`、原文行と一対一）、受付日時、種別、報告者、対象画面、内容の要約、優先度、担当、状態、調査・回答、関連Issue/PR、解決日、追加確認事項、確認した配信コミット。
- 対応履歴タブ：受付番号、更新日時、更新者、変更前後の状態、対応・回答の本文、根拠。対応管理の現在値を更新しても履歴へ追記し、前の回答を消さない。
- 受付番号の自動発番・重複防止・原文行との連携は未実装。並び替えで行番号を取り違えない方式を、アカウント選択後の実送信で検証する。
- 優先度は P0＝二重集金・データ消失・金銭/請求/在庫の重大不整合、P1＝業務が進められない、P2＝操作改善・質問。P0は一次回答で再受取や本番修復を指示せず、原因と影響をWorkへ渡す。
- 通知先は未設定。初期案は同じ報告の反復通知を避け、受付担当への必要最小限の通知だけを選択後に検証する。自動回答の送信・宛先は別途の明示権限が必要。
