# 実機要望の受領・引渡し・完了

正本は [要望台帳](REQUEST_LEDGER.md)。この手順は Chat で受け取る側と Work で実装する側の両方が使う。GitHub のIssue #25は開始時の仕様であり、台帳を更新した代わりにはならない。利用者には台帳の転記・管理・再説明を求めない。

## 受領したその応答内で

1. 利用者の**確定要望／感想・提案／仮説／訂正・撤回**を区別する。現場での不便、欲しい結果、禁止事項、元の言葉を短い要約だけに置き換えない。公開できない氏名・金銭原本・画像本文を台帳へ複写しない。出典の日時・参照先、または会話内の見出しを残す。
2. 最新mainの台帳を読み、同じ目的・同じ症状なら既存IDに出典と再発の経過を追記する。後続の訂正は元の記録を残して新事実と適用時期を追記する。別の目的は次の未使用IDを発行する。本人の一言を「優先度が低い」として落とさない。
3. **その応答内で** GitHub の台帳へ反映し、返却されたコミット／PRのURLを確認する。mainへの保存が必要なら競合を検出して安全に統合し、mainから読み戻してID・出典・意図・状態があることを検査する。PRだけにある場合は「PRに保存、main未反映」と明記する。確認前に登録済みと称しない。
4. 権限不足・通信断・競合なら再試行する。保存できなければ「台帳未保存」と明記し、失われないよう当該要望の元文・ID候補・受入条件を同じ会話の返信に全文残す。後続Workへは「台帳未反映の要望」として含め、保存成功まで未解決扱いにする。利用者の再入力を解決策にしない。

**制約**：別のChatがこのリポジトリやIssue #25を自動で読むことは保証できない。この手順はそのChatが参照した場合の運用契約であり、ChatGPT全体の自動記憶や自動書込みの設定ではない。Work開始時に台帳とIssueを読んで漏れを検出し、保存されなかった発言は参照できる会話・引渡し文と照合する。

## Workへ渡す前・開始時

1. 台帳から今回対象のIDを**全件**列挙し、元の意図・受入条件・禁止・維持条件を指示に入れる。詳細は台帳のIDと見出しへの明示参照でよい。今回入れないIDは理由・継続先を残し、削除しない。
2. 引渡し文に次の固定形式を入れ、元の対象ID集合と照合する。対象IDがまだ台帳未保存ならその全文も含める。

```text
対象ID: WAP-0001, WAP-0002
WAP-0001: 数量欄を狭くし、長い商品名を読める幅とタップ領域を維持する。
WAP-0002: 注文回一覧の太い左線を消さず、状態色の濃い筆跡にする。
今回対象外のID: なし
台帳未反映の要望: なし
```

模擬完了報告での機械照合用対応表：

| ID | 対応結果 | 証拠・残る作業 | 実機確認 |
| --- | --- | --- | --- |
| WAP-0001 | 実装報告あり | `6204a5e` の入力欄とブラウザ検証。更新版の本人確認が残る | 未確認 |
| WAP-0002 | 実装報告あり | `6204a5e` の筆跡とブラウザ検証。更新版の本人確認が残る | 未確認 |

3. Work開始時にmainの台帳・指示・既存実装・テスト・実機欄を照合する。指示にIDがなくても会話で明示された要望を見つけたら、台帳へ記録し指示対象に足す。対象範囲と実変更範囲は別にする。

## 保存・PR・完了時

- PR本文の `対象ID: ...` と各IDの対応表を照合する。`npm run check:docs` は対象IDの存在・対応行・結果・証拠を機械的に検査する。CIが成功しても元の意図・UX品質の意味照合は別に行う。
- IDごとにWork依頼先、変更コミット・テスト・スクリーンショット、前後の操作数、残る作業を台帳へ追記する。未実装、部分完了、実機待ち、再発、判断待ちを区別する。未解決を黙って「完了」に移さない。
- Workの実装報告とブラウザテストは実機欄を `確認済み` にしない。本人の明示的な実機結果があったらその日時・対象版・条件を追記し、失敗なら同じIDを `未解決` に戻す。本人が明示的に撤回した場合のみ理由と原出典を残して `明示的に撤回` とする。

| ID | 元の要望 | 台帳とWork指示 | 実装証拠 | 現在の実機欄 |
